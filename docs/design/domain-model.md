# 도메인 모델: 커맨드·애그리거트·이벤트·뷰·정책

이 문서는 각 컨텍스트 문서가 정한 업무를 다섯 가지 구성 요소로 다시 나눕니다. 구성 요소는 커맨드, 애그리거트, 이벤트, 뷰, 정책입니다. 같은 구조를 먼저 들인 다른 학습 저장소(hemr)를 따르고, 런타임 라이브러리는 쓰지 않습니다([D10](review.md#결정)). 이 문서가 새로 정하는 것은 **어떤 커맨드가 어떤 애그리거트를 바꾸고, 다른 애그리거트에 미치는 영향을 어떤 방식으로 전하는가**입니다. 리소스 필드, 상태 전이표, 오류 코드는 각 컨텍스트 문서에 그대로 둡니다.

## 구성 요소

| 구성 요소 | 뜻 | semu에서의 형태 |
|---|---|---|
| **커맨드** | 도메인에 바꿔 달라는 요청입니다. 명령형으로 이름 짓고, 거부될 수 있으므로 거부 사유를 선언합니다 | `POST /{resource}/{id}:{command}`나 생성·수정 요청 하나([conventions.md](conventions.md#커맨드)). 입력은 Schema, 거부는 오류 코드입니다 |
| **애그리거트** | 함께 지켜야 하는 규칙(불변식)과 그 규칙이 필요로 하는 상태의 묶음입니다. 한 번에 커맨드 하나를 처리하는 일관성 경계입니다 | 저장소 표의 한 행(과 하위 행)입니다. 판정은 순수 함수 `decide`입니다(아래) |
| **이벤트** | 이미 일어난 일의 기록입니다. 과거형으로 이름 짓고, 거부하거나 되돌릴 수 없습니다 | outbox 행입니다([events.md](events.md)). 상태와 같은 트랜잭션에 씁니다 |
| **뷰** | 화면이나 다른 컨텍스트가 읽는 모양입니다 | 읽을 때 표에서 계산합니다. 다른 컨텍스트에는 공개 조회(`<context>.public.ts`)로 내보냅니다 |
| **정책** | 이벤트를 받아 할지 말지 정하고, 커맨드를 보내거나 바깥 시스템을 부르는 규칙입니다. 이미 일어난 일을 거부할 수 없습니다 | outbox 소비자입니다. 최소 1회 전달이므로 멱등이어야 합니다 |

정책 외에 두 가지를 더 씁니다.

- **사가:** 여러 단계로 이어지는 작업에 씁니다. 각 단계는 다른 애그리거트이거나 바깥 기관이고, 뒤 단계가 실패하면 앞 단계를 되돌리거나 실패를 남깁니다. 기관 연동 `Job`([conventions.md](conventions.md#비동기-작업))이 사가의 진행 상태를 담습니다. 수집 요청, 명세서 발송, 세금계산서 발급이 후보입니다
- **예약 커맨드:** 시각이 되면 서버가 스스로 보내는 커맨드입니다. 신고 일정 만들기, 월 결제 예정 만들기, 서명 요청 만료가 여기에 해당합니다. 실행기는 아직 없습니다(#81)

### 애그리거트의 판정 함수

```ts
decide(state, command, context) → { state, events } | 거부
```

- 순수 함수입니다. Effect·저장소·권한을 모릅니다. 시각·행위자·회사와, 서비스가 미리 읽어 둔 사실은 `context`로 받습니다
- 커맨드 처리기(서비스)는 **읽기 → 권한 → `decide` → 저장(상태 + 이벤트, 한 트랜잭션)** 만 합니다
- **거부하면서 남기는 쓰기가 있습니다([M1](#결정)).** 로그인 실패 횟수, 서명자 확인 실패, 거절된 출금 계좌처럼 실패 응답과 함께 남아야 하는 기록입니다. 이런 커맨드의 `decide`는 거부에 남길 상태와 이벤트를 함께 담아 돌려줍니다(`{ rejected, state, events }`). 서비스는 그것을 저장하고 `keepChanges`를 부른 뒤 실패를 돌려줍니다
- **`evolve`(이벤트 → 상태)는 두지 않습니다.** semu는 상태를 저장합니다. 이벤트는 받는 쪽이 판단할 최소 필드만 담고, 주민등록번호 같은 개인정보는 넣지 않습니다. 그래서 이벤트로 상태를 다시 만들 수 없습니다
  - 이 선택으로 잃는 것은 이력에서 상태를 다시 만드는 능력입니다. "왜 이 상태인가"에 대한 답은 신고 건 이력, 급여대장 버전, 감사 로그, 지우지 않는 outbox 행이 맡습니다

### 회사 범위 불변식은 미리 읽은 사실로 넘깁니다

"회사에 관리자가 최소 한 명", "등록된 출금 계좌는 하나", "귀속월마다 정기 급여대장은 하나", "같은 주민등록번호의 직원은 하나"처럼 같은 종류의 여러 행에 걸친 규칙이 많습니다. 회사 전체를 애그리거트 하나로 키우지 않고, 서비스가 그 행들을 읽어 `context`의 사실로 넘깁니다([M3](#결정)).

- 요청 하나가 SQLite 트랜잭션 하나이고 쓰기가 직렬화되므로, 읽은 사실이 판정과 저장 사이에 바뀌지 않습니다
- 사실은 판정에 필요한 만큼으로 줄입니다(`otherActiveAdminCount`, `regularLedgerExists`). 행 목록을 통째로 넘기지 않습니다
- **되돌릴 조건:** PostgreSQL로 옮기거나 쓰기를 여러 프로세스에서 하면([D1](review.md#결정)), 이 규칙들은 유니크 제약이나 회사 단위 카운터 행으로 지켜야 합니다

### 뷰는 읽을 때 계산합니다

같은 SQLite에서 애그리거트 표를 읽어 계산하므로 늦지 않습니다. 저장한 응답을 곧바로 다시 읽는 화면이 많아 이 방식을 기본으로 둡니다.

- 계산이 무거워지면 그 뷰만 별도 표(프로젝션)로 만들고, 갱신은 정책이 맡습니다. 그때는 결과적 일관성이 됩니다
- 급여 **지급월**은 뷰입니다. 저장된 애그리거트가 아니라 회사의 급여대장들에서 계산하고, 지급월 이벤트는 대장 저장 전후의 뷰를 비교해 만듭니다([payroll.md](payroll.md))
- 연동의 마지막 수집 결과(`lastScrap`)는 수집 요청에서 계산하는 뷰 후보입니다

## 일관성 규칙

1. **커맨드 하나는 일관성 경계 하나를 바꿉니다.** 기본 경계는 애그리거트 하나입니다
2. **두 애그리거트에 걸친 불변식이 있을 때만 경계를 묶습니다.** 묶은 경계는 아래 [묶은 경계](#묶은-경계) 표에 올리고, 어떤 불변식 때문인지 적습니다. 묶은 경계의 `decide`는 그 애그리거트들을 함께 받습니다
3. **나머지 영향은 정책으로 전합니다.** 받는 쪽 애그리거트가 자기 `decide`로 판정합니다. 받는 쪽이 거부하면 정책은 그 사실을 기록하고 멈춥니다. 보낸 쪽 커맨드를 되돌리지 않습니다
4. **감사 기록과 개인정보 열람 기록은 커맨드와 같은 트랜잭션에 남깁니다.** 정책으로 옮기지 않습니다. 열람 기록 없이 개인정보가 나가거나, 바뀐 기록이 감사 기록 없이 남는 틈을 만들지 않기 위해서입니다. 이 기록은 애그리거트가 아니라 공유 인프라(`iam_audit_log`, `personal_data_accesses`)입니다
5. **다른 컨텍스트의 애그리거트는 정책으로만 바꿉니다.** 다른 컨텍스트의 상태를 읽어 판정에 쓰는 것(`WithholdingFilingLock`, `SeveranceSettlementLookup`)은 바꾸는 것이 아니므로 `context`의 사실로 넘깁니다

설계 원칙 2("업무 하나 = 요청 하나 = 트랜잭션 하나", [README.md](README.md#설계-원칙))는 2번으로 좁아집니다. 원칙 5(바깥 기관 호출은 `Job`)는 [M8](#결정)대로 아직 일부만 따릅니다. 지금 한 트랜잭션에서 하는 일 중 불변식이 요구하지 않는 것은 정책으로 옮깁니다. 옮기면 응답이나 실패했을 때의 동작이 바뀌는 것은 [결정](#결정)에 따로 적었습니다.

## 애그리거트

키가 같은 행 하나가 인스턴스 하나입니다. 불변식은 그 애그리거트가 혼자 지키는 것과, 미리 읽은 사실로 지키는 회사 범위 규칙(*기울임*)을 적습니다.

### Identity & Access

| 애그리거트 | 키 | 불변식 | 커맨드 |
|---|---|---|---|
| User | `userId` | 비밀번호 정책. 실패 5회면 잠금. *이메일이 겹치지 않음* | 로그인 실패 기록(거부하며 남김), 비밀번호 변경 |
| Session | `sessionId` | 회전된 secret을 다시 쓰면 폐기(거부하며 남김). 만료·폐기 뒤 사용 불가. onboarding token은 1회 | 열기, 갱신, 회사·대리인 전환, 로그아웃, 전부 폐기 |
| Company | `companyId` | 사업자등록번호 검증 숫자. 폐업이면 등록 거부(조회 결과는 `context`). *사업자등록번호가 겹치지 않음* | 등록, 수정 |
| Membership | 회사 + 사용자 | 소유자는 ADMIN 고정. *회사에 ADMIN이 최소 한 명* | 접근 변경, 내보내기 |
| Role | `roleId` | 줄 수 있는 권한만. *회사 안에서 이름이 겹치지 않음* | 생성, 수정, 삭제 |
| Invitation | `invitationId` | `PENDING`일 때만 취소·수락. *같은 이메일로 대기 중인 초대는 하나* | 생성, 취소, 수락 |
| TermAgreement | 사용자(추가만) | 필수 약관은 거절할 수 없음. 지금 버전만 | 응답, 가입 동의 |

| PayrollLedger (+행) | `ledgerId` | 전이표와 워크플로·행위자 권한. 입력은 편집 가능한 상태에서만. 행은 저장할 때 계산. 행의 소득 구분은 바꾸지 않음. `DRAFT`일 때만 삭제. 신고된 달은 잠금(`context`). *귀속월마다 정기 대장 하나, 근로소득 중복 금지* | 생성, 머리 수정, 삭제, 행 추가·수정·삭제, 다시 계산, 전이 |

| PayrollSetting | 회사 | 패치 규칙 | 수정 |
| PayslipSend | 회사 + 멱등 키 | 같은 키는 같은 결과 | 발송(사가 후보) |

수집 반입(`ScrapedRecordIngestion`)은 커맨드가 아니라 바깥 기록을 들이는 경계(반부패 계층)입니다. 일괄 분류는 같은 종류 애그리거트 여러 개에 같은 커맨드를 보내는 것으로 보고, 한 트랜잭션에서 모두 되거나 모두 안 됩니다.

### Assistant

대화(Conversation)는 덧붙이기만 하는 기록이고 모델 응답은 바깥 결과(`context`)라 판정 구조로 얻는 것이 적습니다. 옮기지 않거나 맨 마지막에 옮깁니다.

## 묶은 경계

| 묶음 | 불변식 | 묶지 않으면 생기는 일 |
|---|---|---|
| 회사 등록: Company + Membership(소유자) | 회사에는 소유자 ADMIN이 있습니다 | 관리자가 없는 회사가 남습니다 |
| 초대 수락: Invitation + Membership (+가입이면 User·TermAgreement) | `ACCEPTED`인 초대에는 소속이 있습니다 | 수락했는데 회사에 들어가지 못합니다 |
| 권한 변경 + 토큰 폐기: Membership·Role·TermAgreement·User 비밀번호 + Session | 권한이 줄면 그 순간부터 옛 토큰으로 할 수 없습니다([M5](#결정)) | 권한을 뺀 뒤에도 정책이 돌 때까지 옛 권한으로 쓸 수 있습니다 |
| 출금 계좌 교체: BillingMandate(새) + BillingMandate(이전) | 회사에 `REGISTERED` 계좌는 하나입니다 | 출금 계좌가 둘이 됩니다 |
| 직원 배치: Employee + OrganizationUnit(`everAssigned`) | 한 번이라도 배치된 단위는 삭제할 수 없습니다. 표시는 한 번 켜면 끄지 않는 저장값이라 지금 배치에서 계산할 수 없습니다 | 배치한 뒤 정책이 돌기 전에 직원을 옮기면 원래 단위를 지울 수 있습니다 |
| 직원 삭제: Employee + FamilyMember | 직원 없는 가족 개인정보를 남기지 않습니다 | 주민등록번호가 주인 없이 남습니다 |
| 계정과목 생성·삭제: AccountTitle + Evidence·BankTransaction 분류 + ClassificationRule | 분류는 하위가 없는 계정만 가리키고, 지운 계정을 가리키지 않습니다 | 장부가 없는 계정을 가리킵니다 |
| 서명 문서 반영: EmployeeDocument + WorkContract·PayrollContract 서명 연결 | 무효인 문서는 계약에 연결되지 않고, 계약은 그 문서가 유효할 때만 그 문서를 가리킵니다 | 무효가 된 서명이 계약에 남습니다. 정책 하나가 HR 안에서 한 트랜잭션으로 처리합니다 |
| 지로 납부: Giro + 납부 시도 | `DONE`이면 성공한 납부가 있습니다 | 납부 기록 없는 완료가 생깁니다 |

정산 연결은 입출금 거래의 하위 행, 자료 항목·문서·이력은 신고 건의 하위 행이므로 묶음이 아닙니다.

굵게 쓴 것이 커맨드가 바꾸는 경계입니다. 오른쪽은 그 밖에 생기는 일과, 그 일을 무엇이 맡는지입니다.

## 이벤트

이벤트 목록은 [events.md](events.md#이벤트-목록)와 각 컨텍스트 문서가 단일 출처입니다. 이 구조에서 덧붙이는 규칙만 적습니다.

- 이 문서의 표에 있지만 events.md에 없는 이름(`role.deleted`, `invitation.created`, `partner.created`, `scrap.item_succeeded`, `family_member.changed`, `employee.deleted`, `employee.resignation_canceled`, `social_insurance_setting.changed`, `filing.document_viewed`)은 설계 단계 이름입니다. 그 정책을 옮기는 PR이 이름과 payload를 정해 events.md에 올립니다

- 이벤트는 그것을 낸 애그리거트의 `decide`가 만듭니다. 서비스가 이벤트를 직접 조립하지 않습니다
- 정책이 판단에 쓰는 필드는 payload에 넣습니다. 개인정보는 넣지 않고, 필요하면 정책이 애그리거트를 읽습니다
- 지금 Tax의 `filing.status_changed`는 메모리에만 쌓이고 사라집니다. 할 일 카드 정책([M4](#결정))을 옮길 때 outbox로 냅니다

## 정책

정책은 [M2](#결정)의 실행기에 등록합니다. 아래 "지금"이 outbox 채널이면 이미 정책이고, 실행기를 만들 때 옮깁니다.

| 정책 | 받는 이벤트 | 보내는 커맨드 | 받는 쪽이 거부하면 | 지금 |
|---|---|---|---|---|
| 원천세 급여대장 항목 | `payroll_pay_month.*` | 신고 건 급여대장 항목 다시 맞춤 | 없음(다시 계산이라 거부하지 않음) | outbox `payroll_pay_month->tax` |
| 서명 완료 반영 | `esign_request.completed`·`voided` | 직원 문서 넣기·무효, 계약 서명 연결·풀기 | 기록만 합니다(직원이 없으면 문서만 남김) | outbox `esign_request->hr` |
| 할 일 카드 | `filing.status_changed`, `filing.document_viewed` | 카드 열기·닫기 | 기록만 합니다 | 같은 트랜잭션 |
| 4대보험 신고 맞추기 | `employee.*`, `leave.*`, `family_member.changed`, `*_contract.changed`, `social_insurance_setting.changed` | 직원 단위로 열린 신고 맞추기 | 기록만 합니다 | 같은 트랜잭션 |
| 역할 떼기 | `role.deleted` | 소속에서 역할 제거 | 없음 | 같은 트랜잭션 |
| 초대 메일 | `invitation.created` | 메일 발송 | 실패를 남기고 재시도 | 요청 안에서 호출 |
| 수집 반입 | `scrap.item_succeeded` | 경리 반입 | 실패를 남기고 재시도. 반입은 `externalKey`로 멱등 | 요청 안에서 호출 |
| 거래처 연결 | `partner.created` | 증빙에 거래처 연결 | 없음 | 같은 트랜잭션 |
| 매출 증빙 | `tax_invoice.issued` | 증빙 만들기 | 없음 | 같은 트랜잭션 |
| 플랜 반영 | `subscription.changed` | 그 회사 토큰 폐기 | 없음 | 미구현(D6) |

- **정책의 행위자는 받은 이벤트의 행위자입니다.** 정책이 남기는 감사 기록과 이벤트의 행위자는 처음 커맨드를 보낸 사용자입니다
- **정책이 돌기 전의 틈은 받는 쪽 애그리거트가 막습니다.** 예: 삭제된 직원의 신고는 정책이 철회하기 전에도 대리인이 완료할 수 없어야 합니다. 정책을 옮기는 PR이 틈마다 막는 방법을 적습니다

## 코드 배치

저장소는 이미 종류를 접미사로 붙입니다([conventions.md](conventions.md#코드-구조)). 같은 방식으로 이렇게 둡니다.

| 파일 | 담는 것 |
|---|---|
| `filing.aggregate.ts` | 상태 형, 커맨드 입력, 거부, `decide`, 허용 동작 |
| `account-title-deletion.aggregate.ts` | 묶은 경계의 `decide`. 이름은 커맨드를 따릅니다 |
| `filings.ts` | 커맨드 처리기(서비스): 읽기 → 권한 → `decide` → 저장 |
| `<name>.view.ts` | 뷰 계산 |
| `<name>.policy.ts` | 정책: 받는 이벤트, 판단, 보내는 커맨드 |
| `*.api.ts`, `*.http.ts` | 그대로 |

- 애그리거트 파일은 규칙 계산 모듈입니다. Effect에 의존하지 않고, 내보내지 않는 이름은 한글로 쓸 수 있습니다([conventions.md](conventions.md#코드의-용어))
- 판정 함수의 테스트는 저장소 없이 given/when/then으로 씁니다(`*.aggregate.test.ts`)
- 이미 순수 함수인 규칙 모듈(`filing-status.ts`의 `transitionFiling`, `ledger-status.ts`의 `decideTransition`, 세액 계산 엔진)은 `decide`가 부르는 쪽으로 둡니다. 파일 이름은 바꾸지 않습니다

## 단계

1. **시범: Tax 신고 건.** `filing.aggregate.ts`로 옮기고 동작은 바꾸지 않습니다. 전이표·자료 항목 판정이 이미 순수 함수라 옮길 양이 작고(서비스의 약 150~200줄), 행위자 규칙과 하위 행(자료 항목·문서·이력)이 있어 규약을 정하기 좋습니다. 이 문서의 규약을 확정합니다
2. **나머지 애그리거트.** 묶은 경계 표의 묶음과 거부하며 남기는 커맨드(M1)부터 옮깁니다. 컨텍스트 묶음마다 PR 하나이고 동작은 바꾸지 않습니다. 순서는 Payroll → HR → Documents → Identity & Access → Billing → Integrations → Bookkeeping입니다
3. **정책 기반.** 이벤트 행과 정책별 커서, 정책 실행기를 만들고([M2](#결정)) 지금 있는 채널 둘을 정책으로 옮깁니다
4. **트랜잭션에서 정책으로 옮기기.** 위 [정책](#정책) 표의 "같은 트랜잭션"·"요청 안에서 호출"을 하나씩 옮깁니다. 응답이 바뀌는 것은 컨텍스트 문서를 함께 고칩니다

| # | 질문 | 선택지 | 결정 |
|---|---|---|---|
| M1 | 실패 응답과 함께 남기는 쓰기를 판정에 어떻게 담는가 | 서비스에 둠 / 판정의 거부에 담음 | **결정: 판정의 거부에 담음.** 로그인 실패 잠금, 서명자 확인 잠금, 계좌 거절은 업무 규칙이라 서비스에 두면 판정이 둘로 나뉩니다. 거부는 남길 상태와 이벤트를 함께 가질 수 있고, 서비스는 저장 뒤 `keepChanges`를 부릅니다 |
| M2 | outbox를 어떤 모양으로 두는가 | 지금처럼 이벤트 × 소비자 행 / 이벤트 한 행 + 정책별 커서 | **결정: 이벤트 한 행 + 정책별 커서.** 지금은 내는 쪽 어댑터가 소비자를 골라 소비자를 늘리려면 내는 쪽을 고쳐야 하고, 실패한 행을 건너뛰어 같은 리소스의 이벤트 순서가 바뀔 수 있습니다. 정책마다 `seq` 순서로 읽고, 결함이 나면 그 정책만 그 이벤트에서 멈춥니다. 지금의 재시도 횟수·죽은 이벤트 표시와 운영 절차([conventions.md](conventions.md#코드-구조))는 (정책, 이벤트) 단위로 옮깁니다. 바꾸는 일은 3단계에서 합니다 |
| M3 | 회사 범위 불변식을 어디서 지키는가 | 회사 단위 애그리거트 / 미리 읽은 사실(`context`) | **결정: 미리 읽은 사실.** 회사 단위로 묶으면 관계없는 커맨드가 한 버전을 두고 다툽니다. SQLite 한 프로세스에서는 읽은 사실이 판정과 저장 사이에 바뀌지 않습니다. 되돌릴 조건은 [위](#회사-범위-불변식은-미리-읽은-사실로-넘깁니다)에 적었습니다 |
| M4 | 신고 건 전이가 할 일 카드를 같은 트랜잭션에서 바꾸는가 | 묶음 유지 / 정책 | **결정: 정책.** 카드는 신고 건에서 파생되는 할 일이고 같은 순간에 지켜야 할 불변식이 없습니다. 대가: 전이 응답 직후 카드 목록이 정책이 돌 때까지 늦게 바뀝니다. [tax.md](tax.md)와 [events.md](events.md)의 "같은 요청에서 바뀜"은 옮길 때 고칩니다 |
| M5 | 권한 변경이 토큰 폐기를 같은 트랜잭션에서 하는가 | 묶음 유지 / 정책 | **결정: 묶음 유지.** 권한 회수는 그 순간부터 지켜야 하는 보안 불변식이고, 같은 컨텍스트 안입니다. 플랜 변경(D6)은 다른 컨텍스트라 정책입니다 |
| M6 | HR 커맨드가 4대보험 신고를 같은 트랜잭션에서 여는가 | 묶음 유지 / 정책 | **결정: 정책.** 신고 큐는 공단에 낼 할 일이고 직원 기록의 불변식이 아닙니다. 다섯 서비스에 흩어진 맞추기 로직을 정책 하나로 모으고, 4대보험 설정·근로계약 변경 때 보수 변경 신고를 맞추지 않는 빈틈도 함께 메웁니다. 대가: 직원 등록 응답 직후 신고 큐가 늦게 채워집니다 |
| M7 | 수집 요청이 요청 안에서 워커를 돌리는가 | 그대로 / Job + 정책 | **결정: Job + 정책.** 지금 다른 컨텍스트(Bookkeeping)에 동기로 쓰는 유일한 경로입니다. 대가: 수집 요청 응답은 `QUEUED`로 돌아오고 결과는 Job으로 봅니다 |
| M8 | 바깥 호출(서명 링크 발송, PDF 렌더링, 명세서 메일, 세금계산서 발급, 지로 납부, CMS 출금 계좌 등록)을 요청 안에서 하는가 | 그대로 / 사가 | **결정: 지금은 그대로 두고 결과를 `context`로 넘김.** 발송 실패(`SEND_FAILED`)를 응답에서 바로 보여 주는 동작이 각 문서의 계약입니다. 판정은 바깥 결과를 받아 하므로 `decide`는 순수하게 둘 수 있습니다. **다시 볼 조건:** 바깥 호출이 느려 트랜잭션이 쓰기 잠금을 오래 쥐거나, 재시도 스케줄러(#81)가 생기면 사가로 옮깁니다 |
