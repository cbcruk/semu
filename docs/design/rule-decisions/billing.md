## subscription-entitlement

| # | 질문 | 결정 | 내용 |
|---|---|---|---|
| 1 | 구독 항목의 실제 필드, `free` 코드가 있는지 | 바꿈 | 구독 리소스 전체(`plan`, `status`, `isEntitled`, 기간, 월 이용료)를 줌. 무료는 상품이 아니라 "유료 플랜 없음" 상태 |
| 2 | `me.companies[].taxPlan`이 다른 값을 갖는지, 세무 구독과 늘 같은지 | 바꿈 | `taxPlan`을 없애고 `/me`의 `company.plans` 하나로 줌. 구독에서만 계산 |
| 3 | 모르는 코드를 구독하면 `isFree: false`가 되는 의미 | 바꿈 | `isFree` = 유료 플랜이 하나도 없음. 상품은 enum이라 모르는 코드가 오지 않음 |
| 4 | 해지 예약 중 종료일까지 플랜 유지 | 따름 | 종료일(포함)까지 유지. 날짜 경계는 Asia/Seoul |
| 5 | 누가 구독을 바꾸고 언제 반영되는지 | 가정 | 담당자 커맨드(대리인 전용 `subscription:manage`)만 둠. 반영은 날짜 기준 즉시(읽을 때 계산). 학습용 가정: 데스크 운영 방식은 내부 자료라 받을 수 없고, 현행에 고객용 구독 변경 화면이 없습니다 |

### 바뀌는 케이스

| 케이스 | 현행 기대값 | 서버 기대값 |
|---|---|---|
| unknown subscribed code is neither free nor a plan | `isFree: false` | `isFree: true` |
| pending even after the start date | `false` | `true` |

픽스처 테스트: `apps/api/src/modules/billing/subscriptions/subscription-entitlement.fixtures.test.ts`. 옮기지 않은 케이스는 없습니다.

### 결정 기록

**플랜의 원본 (1, 2, 3)**

- 결정: 플랜은 Billing 구독 하나에서 `entitledPlans(subscriptions, today)`로 계산하고, Identity & Access는 `CompanyPlans` 포트로 토큰 발급 때마다 읽습니다. `isFree`는 `/me`의 `promotions` 판정에 서버가 씁니다
- 검토한 대안: 레거시처럼 회사에 `tax_plan`·`has_payroll_plan` 캐시를 두고 구독 변경 때 갱신. 클라이언트가 구독 목록에서 플래그를 계산
- 선택 이유: 같은 사실이 세 곳에 있으면 갱신 누락으로 어긋납니다. 계산 비용은 회사당 구독 몇 건이라 매번 계산해도 됩니다
- 가정과 되돌릴 조건: 유료 상품이 세무·급여 둘뿐이라는 가정입니다. 새 상품이 생기면 `Plan`에 값을 더하고, 무료와 다른 "부분 유료" 의미가 필요하면 `isFree` 대신 상품별 플래그를 줍니다

**날짜 전이를 읽을 때 계산 (5, 바뀌는 케이스 2)**

- 결정: `PENDING → ACTIVE`, `→ ENDED`처럼 날짜로 정해지는 전이는 저장값을 기다리지 않고 `refreshedStatus(subscription, today)`로 읽을 때 계산합니다. 그래서 시작일이 된 `PENDING`은 매일 작업 전에도 플랜을 줍니다
- 검토한 대안: 레거시처럼 매일 작업이 상태를 바꾸고 판정은 저장된 상태만 봄(`pending`이면 시작일이 지나도 미구독)
- 선택 이유: 설계 원칙 3(날짜로 계산되는 상태는 서버가 파생)과 같습니다. 작업이 늦거나 실패해도 시작일에 기능이 열립니다
- 가정과 되돌릴 조건: 시작일이 곧 이용 개시라는 가정입니다. 담당자의 개시 확인이 따로 필요하다면 `PENDING`에서 `:activate` 커맨드를 두고 날짜 전이를 뺍니다

**해지 예약 (4)**

- 결정: `CANCELLATION_SCHEDULED`는 `endsOn`(포함)까지 플랜을 유지하고 다음 날 `ENDED`가 됩니다. 시작 전 구독을 해지하면 바로 `ENDED`입니다. `:resume`으로 해지 예약을 거둘 수 있습니다
- 검토한 대안: 해지하는 순간 플랜 회수
- 선택 이유: 이미 낸 달의 이용료만큼 쓰게 하는 것이 일반적이고 레거시 제안과 같습니다
- 가정과 되돌릴 조건: 계약상 즉시 해지가 있으면 `:cancel`에 `effective: IMMEDIATE`를 더합니다

**구독 변경 주체 (5)**

- 결정: 구독 시작·해지 예약·철회는 세무 대리인 담당자만 합니다. 고객 관리자는 `*` 권한이 있어도 거절합니다. `subscription:manage`가 카탈로그의 대리인 전용(`agentOnly`)이라 `*`가 덮지 않고 대리인 기본 권한에만 있습니다(D5, 2026-11-06 전에는 `actor.kind`로 따로 막았습니다)
- 검토한 대안: 고객 셀프 해지. 계약 서명 시 자동 시작만 허용
- 선택 이유: 현행에 고객용 구독 변경 화면이 없고 레거시도 담당자 전용입니다
- 가정과 되돌릴 조건: 데스크 운영 방식을 알 수 없어 학습용 가정으로 정했습니다(2026-11-07). 계약 서명으로 자동 시작한다면 `billing.service-contract.signed`를 받아 같은 서비스로 시작합니다

## payment-schedule

| # | 질문 | 결정 | 내용 |
|---|---|---|---|
| 1 | 출금일(레거시 25일)의 실제 값 | 가정 | `BILLING_DAY = 25` 유지. 학습용 가정: CMS 출금 계약은 받을 수 없어 레거시 값을 씁니다. 계약별 값이 필요해지면 서비스 계약으로 옮김 |
| 2 | D-1 알림이 달력일인지 영업일인지 | 따름 | 미룬 출금일의 하루 전 달력일 (`noticeDate`) |
| 3 | 급여 아웃소싱만 보여 주는 주체 | 가정 | 서버가 거름(`LISTED_PAYMENT_PLANS = ['PAYROLL']`). 학습용 가정: 세무 기장료는 CMS가 아닌 별도 청구로 봅니다. 현행 화면과 같은 결과입니다 |
| 4 | 재시도가 같은 번호인지 자식 결제인지 | 바꿈 | 같은 결제를 `FAILED → RETRYING`으로 바꾸고 출금일만 옮김. 번호 유지, 자식 결제 없음 |
| 5 | 부분 환불 | 가정 | 전액 환불만. `REFUNDED` 하나. 학습용 가정: 약관·운영 정책은 받을 수 없어 더 단순한 쪽을 고릅니다 |
| 6 | 월 중간 시작·종료의 일할 계산 | 가정 | 일할 없음. 출금일에 이용 가능하면 월 이용료 전액. 학습용 가정: 약관·계약의 일할 조항은 받을 수 없어 더 단순한 쪽을 고릅니다 |

### 바뀌는 케이스

없음. 픽스처의 409 `INVALID_TRANSITION`은 코드 이름만 `PAYMENT_TRANSITION_INVALID`로 바뀌고, 픽스처 테스트는 전이가 거절되는지(`undefined`)로 봅니다.

옮기지 않은 케이스: `status labels`(표시 문자열은 클라이언트 i18n). 픽스처 테스트: `apps/api/src/modules/billing/payments/payment-schedule.fixtures.test.ts`.

### 결정 기록

**출금일과 영업일 (1, 2)**

- 결정: 출금일은 그달 25일에서 시작해 주말·공휴일을 넘깁니다(`billingDate`). 공휴일은 `PublicHolidays` 포트로 받고, 결과 반영일은 출금 다음 날, 알림은 출금 전날입니다
- 검토한 대안: 계약마다 출금일. 알림을 직전 영업일에
- 선택 이유: 매뉴얼은 "비영업일이면 다음 영업일"만 말하고 날짜는 레거시 제안뿐입니다. 알림톡은 은행망이 아니라 휴일에도 보낼 수 있습니다
- 가정과 되돌릴 조건: 출금일이 모든 고객에게 같다는 가정입니다. 계약별 출금일이 확인되면 `ServiceContract.billingDay`로 옮기고 `plannedPayments`가 그것을 받게 합니다

**결제 내역 범위 (3)**

- 결정: 결제 목록과 상세는 `PAYROLL` 결제만 줍니다. 목록에 없는 결제는 404입니다
- 검토한 대안: 모두 주고 클라이언트가 거름
- 선택 이유: 표시 정책도 서버가 정한다는 원칙(P1)입니다. 현행 화면과 같은 결과를 냅니다
- 가정과 되돌릴 조건: 세무 기장료가 CMS가 아닌 별도 청구라는 가정입니다. 세무 결제도 CMS로 걷는다면 `LISTED_PAYMENT_PLANS`에 `TAXATION`을 더합니다

**재시도 모델 (4)**

- 결정: 재시도는 같은 결제의 상태 전이입니다. `scheduledOn`을 새 출금일(지정일 또는 내일의 다음 영업일)로 옮기고 `failureReason`을 지웁니다. 담당자 전용이고 `Idempotency-Key`가 필요합니다
- 검토한 대안: 레거시 제안처럼 `parent_payment_id`를 가진 새 결제
- 선택 이유: 픽스처 전이(`failed → retrying → paid | failed`)가 한 결제의 상태로 정의되어 있고, 화면의 결제 번호가 바뀌지 않아야 고객이 같은 건으로 압니다
- 가정과 되돌릴 조건: 재시도 이력은 감사 로그로 충분하다는 가정입니다. 회계상 시도마다 별도 기록이 필요하면 `payment_attempts` 하위 기록을 두되 결제 번호는 유지합니다

**환불·일할 (5, 6)**

- 결정: 전액 환불만 두고, 일할 계산 없이 출금일 기준으로 월 이용료를 청구합니다
- 검토한 대안: `refundedAmount`로 부분 환불, 일 단위 일할
- 선택 이유: 매뉴얼에 부분 환불·일할 언급이 없습니다
- 가정과 되돌릴 조건: 계약서에 일할 조항이 있으면 `plannedPayments`에 기간 비율을 넣고, 부분 환불이 있으면 `PARTIALLY_REFUNDED` 상태를 더합니다
