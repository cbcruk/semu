# 규제 요구가 설계에 주는 제약

세법·노동법·개인정보 법령이 데이터 모델과 API에 직접 영향을 주는 부분만 정리했습니다. 법률 자문이 아니며, **구현 전에 국가법령정보센터 원문을 다시 확인해야 합니다.** 조문 번호와 기간 중 "(확인 필요)"로 표시한 것은 이 문서를 쓰면서 원문으로 확인하지 못한 값입니다.

## 장부와 증빙 보존

- **근거:** 국세기본법 제85조의3(장부 등의 비치와 보존)은 거래에 관한 장부와 증거서류를 법정신고기한이 지난 날부터 5년간 보존하도록 정합니다. 소득세법·법인세법·부가가치세법에도 같은 취지의 보존 규정이 있습니다 (확인 필요: 이월결손금 공제 시 10년 등 예외)
- **설계 반영**
  - 매출·매입 증빙, 입출금, 세금계산서, 지로 납부, 결산 보고서는 삭제 API를 두지 않습니다. 잘못 들어온 증빙은 `EXCLUDED` 상태로 남기고 집계에서만 뺍니다 ([bookkeeping.md](bookkeeping.md))
  - 발행한 세금계산서는 고치지 않고 수정세금계산서를 새로 발행합니다
  - 보존기간은 코드에 박지 않고 `retention-policies` 참조데이터(종류 → 기간, 기산점)로 둡니다. 기간이 지난 데이터는 파기 작업(Job)으로 처리하고 파기 대장을 남깁니다

## 신고와 원천징수

- **근거:** 소득세법 제164조(지급명세서 제출), 제164조의3(간이지급명세서 제출), 제128조(원천징수세액의 납부). 간이지급명세서는 사업·일용·근로소득별로 제출 주기가 다릅니다 (확인 필요: 2026년 기준 월별·반기별 주기)
- **설계 반영**
  - 지급명세서를 다시 만들 수 있도록 급여대장의 **행 단위 원본**(성명, 주민번호, 내외국인, 거주국, 업종코드, 지급액, 세액, 근무일수)을 마감 뒤에도 보존합니다 ([payroll.md](payroll.md))
  - 원천세 신고가 `FILED` 이상이면 해당 지급월 급여대장의 재계산·반려·추가를 막고, 바꾸려면 수정신고 흐름을 거칩니다 ([tax.md](tax.md), [events.md](events.md))
  - 신고 건은 덮어쓰지 않고 상태 이력과 제출 파일 버전을 남깁니다

## 근로계약서와 임금명세서

- **근거:** 근로기준법 제17조(근로조건의 명시, 서면 교부), 제42조(계약 서류의 보존, 3년), 제48조제2항(임금명세서 교부)
- **설계 반영**
  - 근로계약서·급여계약서는 전자서명이 끝나면 버전을 고정하고, 고치려면 새 계약을 만듭니다 ([hr.md](hr.md), [documents.md](documents.md))
  - 서명 완료 문서와 서명 증적(서명 시각, 본인확인 방법, 해시)은 3년 이상 보존합니다. 퇴직 후에도 남깁니다
  - 임금명세서는 급여대장 확정 시점의 값으로 만들고, 교부(이메일·알림톡) 이력을 남깁니다. 대장을 다시 열어 고치면 새 명세서를 다시 교부합니다

## 전자서명

- **근거:** 전자서명법, 전자문서 및 전자거래 기본법 (확인 필요: 근로계약 전자서명의 본인확인 수준 요건)
- **설계 반영**
  - 서명 링크 토큰은 해시만 저장하고, 본인확인(이름 + 생년월일 또는 외부 본인확인)에 성공해야 서명 세션을 줍니다. 실패 횟수 제한은 서버가 셉니다
  - 서명 완료 처리(계약 생성, 문서 보관함 저장)를 클라이언트에 맡기지 않고 `:complete` 커맨드 하나의 트랜잭션으로 처리합니다

## 개인정보 최소 노출

- **근거:** 개인정보 보호법 제24조의2(주민등록번호 처리 제한·암호화), 제29조(안전조치의무), 개인정보의 안전성 확보조치 기준 (확인 필요: 접속기록 보관 기간 1년/2년 기준). 원천징수·4대보험 신고는 법령에 근거한 주민등록번호 처리입니다
- **설계 반영**
  - 주민등록번호·외국인등록번호·여권번호·계좌번호는 필드 단위로 암호화합니다. 응답에는 기본으로 마스킹 값(`registrationNumberMasked`, `accountNumberMasked`)만 넣고, 원문은 `X-Access-Reason` 헤더를 받는 별도 엔드포인트로만 줍니다
  - 중복 직원 확인은 비밀 키를 쓴 HMAC-SHA256 해시로 합니다. 암호문은 비교할 수 없고, 평문 해시는 사전 공격에 약하기 때문입니다
  - **현재 구현:** 서버(`SqliteLive`)는 AES-256-GCM(값마다 새 IV, 암호문 `v2:<iv>:<tag>:<ciphertext>`)으로 암호화하고 용도 문자열을 AAD로 묶습니다. 키는 서버 데이터 키 하나(`DataKey`, `src/shared/crypto/`)에서 용도마다 HKDF-SHA256으로 따로 만듭니다(HR 주민등록번호, HR 계좌번호, HR 중복 판정 HMAC, Bookkeeping 회사 계좌·거래처 계좌·지로 출금 계좌, Integrations 자격 증명). 바뀐 암호문이나 다른 필드로 옮긴 암호문은 GCM 태그 검사에서 거절하고, 원인(용도와 종류만)을 로그에 남깁니다. 그 밖의 결함은 메시지에 저장 값(이름·이메일)이 섞일 수 있어 오류 이름과 코드 위치만 남깁니다(`src/shared/problem/defect-log.ts`). 행 단위 바인딩(`companyId`·레코드 ID를 AAD로)은 아직 하지 않습니다
  - 데이터 키는 환경 변수 `SEMU_DATA_KEY`(base64 32바이트, 엄격한 형식 검사)로 넣습니다. 없으면 서버가 데이터베이스 옆에 `semu.key`(권한 0600)를 만들어 다시 쓰고 경고를 남깁니다. 권한이 0600보다 넓은 키 파일은 거부합니다. 데이터가 이미 있는 데이터베이스 옆에서는 새 키 파일을 만들지 않고 시작을 거부합니다. 데이터베이스(`semu_meta`)에 키 지문(파생 키의 HMAC)을 남겨 두고, 다른 키로 띄우면 시작하지 않습니다. 지문 없이 데이터가 있는 데이터베이스(데이터 암호화 이전에 만든 것)도 어떤 키로 쓴 것인지 알 수 없으므로 지금 키를 받아들이지 않고 시작을 거부합니다. 지우고 다시 만들어야 합니다. 빈 새 데이터베이스는 지금 키의 지문을 남깁니다. `SEMU_DATABASE=memory`는 프로세스마다 새 키를 씁니다. 키를 잃으면 저장된 암호문을 열 수 없으므로 운영에서는 KMS가 이 키를 감싸 보관해야 합니다 (KMS 연동은 아직 없음)
  - 결정적인 가짜 암호화(`layerFake`, 고정 키 금고)는 테스트와 컨텍스트 단위 실행(`MemoryLive`)에만 씁니다
  - 이벤트 payload에 주민번호·계좌번호·급여 금액을 넣지 않습니다. 소비자는 ID로 다시 조회합니다 ([events.md](events.md))
  - 엑셀 내보내기와 급여 명세 열람은 사유 헤더 + 감사 기록을 남깁니다
  - 이메일·전화번호처럼 화면에 보여야 하는 값도 공개 경로(서명 링크, 초대 확인)에서는 마스킹합니다

## 외부 기관 자격 증명

- **근거:** 전자금융거래법, 개인정보 보호법 제29조 (확인 필요: 공동인증서 위탁 보관의 허용 범위)
- **설계 반영**
  - 홈택스·은행·카드 연동 비밀번호, 인증서 키와 비밀번호, PG 키, CMS 출금 계좌는 봉투 암호화(데이터 키를 KMS 마스터 키로 래핑, `keyVersion` 회전)로 저장하고 응답에 넣지 않습니다
  - **현재 구현:** 서버의 `CredentialVault.layerDataKey`가 서버 데이터 키에서 파생한 자격 증명용 키로 AES-256-GCM 봉인합니다. KMS 래핑은 아직 없습니다 ([개인정보 최소 노출](#개인정보-최소-노출)의 키 출처와 같음)
  - 인터넷지로 ID·비밀번호는 저장하지 않고 연동 요청에만 통과시킵니다 (매뉴얼 명시)
  - 연동을 지우면 자격 증명은 즉시 파기하고, 수집 이력은 보존합니다 ([integrations.md](integrations.md))
  - 인증서는 사업자·대표자 명의와 용도가 맞을 때만 등록합니다. 판정은 서버가 합니다

## 권한 범위와 대리인

- **근거:** 세무사법(세무대리 업무 범위), 개인정보 보호법 제26조(업무위탁) (확인 필요: 수임 동의와 위탁 계약의 관계)
- **설계 반영**
  - 세무 대리인 직원은 배정된 회사에만 접근하고, 그 회사의 액세스 토큰으로만 동작합니다. 모든 동작은 감사 로그에 `actor.kind = AGENCY`로 남습니다 ([identity-access.md](identity-access.md))
  - 홈택스 수임동의 상태를 서버가 갖고, 동의가 없는 회사의 홈택스 수집은 거절합니다

## AI 비서

- AI 비서가 제안한 쓰기 동작(세금계산서 발행, 증명서 요청)은 바로 실행하지 않고 사용자 확인을 거칩니다 ([assistant.md](assistant.md))
- 외부 모델에 보내는 데이터에는 주민번호·계좌번호를 넣지 않습니다. 대화 보존 기간과 외부 전송 여부는 약관 동의에 맞춰야 합니다 (정책 결정 필요, [review.md](review.md#결정-필요))
